The streaming kitchen

Apache Flink® SQL for pizza shops: the recipes, and the science behind them

Each recipe starts with a question the business needs answered, gives the SQL, and then shows everything Flink does with it: every operator, every row, every piece of state, and every timer, step by step. The job graphs come from Flink's planner, and the animations were checked against Flink itself.

    Before you start

    These recipes assume you know SQL well, and have some experience with Apache Kafka® and stream processing. These are the topics the page relies on most.

    SQL
    GROUP BY, joins, and window functions such as ROW_NUMBER() OVER (PARTITION BY … ORDER BY …), which deduplication relies on.
    Kafka
    Topics, keys, and partitions. For the upsert examples, how a compacted topic keeps the latest value for each key, and how a null value (a tombstone) deletes it.
    Event time and watermarks
    Why events arrive out of order, and how a watermark decides when a time-based result, such as a window, is complete.
    Changelogs
    A Flink SQL query over a stream produces a stream of changes, not a result set. Understanding why some results are append-only, and others are updated, is the key to most of these recipes.

    How to read the diagrams

    Every recipe is a Flink job: an Apache Kafka® source on the left, a Kafka sink on the right, and the operators the Flink SQL planner chose in between.

    Stream types
    Each edge's chip lists the row kinds it can carry, and its color gives the stream type.
    +I append-only: only inserts. Each record is a new fact.
    +I +U −D upsert: inserts, updates and deletes, by key. An update replaces the row with the same key.
    +I −U +U −D retract: every update is sent as a pair: retract the old row, then add the new one.
    Row kinds
    +I insert
    −U retract the old version
    +U the new version
    −D delete
    Watermarks
    WM 12:00:04 travels with the data and says no record at or before this time should follow. Operators that wait for time use watermarks to know when to act.
    Operators
    stateless handles each record on its own, and keeps nothing.
    stateful keeps keyed state, shown underneath it.
    added by the planner isn't in your SQL, but the planner needs it to produce correct results. Calc nodes that only drop columns, or set up a time attribute, are left out. hash(store_id) under an edge means the records are repartitioned by that key, so every record for a key reaches the same parallel instance.

    Each diagram has a Help button that brings this up beside it, and hovering over a stream type, a watermark, or a stateful operator explains it.

    Summary

    Every recipe at a glance: the state it keeps, what it uses watermarks for, the watermark it sends downstream, the stream it writes, and the operators the planner adds. Each row links back to its animation.

      Job graphs and changelog modes are checked with EXPLAIN CHANGELOG_MODE on Apache Flink 2.3.0. Every animation except the lookup join, which needs an external service, is also replayed through Flink: the rows each sink receives are compared with the animation's, and each stateful operator is run on the same inputs, one step at a time, to compare what it emits, what it keeps in state, and its timers. LATERAL SNAPSHOT is checked on a 2.4 snapshot build, and deduplication ordered by order_id on a 2.3 snapshot build, for a planner fix in 2.3.1. The animations simplify how Flink schedules work, but not what each operator does.
